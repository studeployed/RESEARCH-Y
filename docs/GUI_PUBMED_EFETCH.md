# P1-06h2 — Explicitly consented PubMed EFetch metadata and abstract retrieval

**Baseline:** owner-merged PR #66, `main` at `7b9e78f25b769887cdb987d2eb307ff6f459b3f9` on 4 November 2026.
**Authority:** version-controlled `RESEARCH-Y_SPEC.md`, SEARCH-06–14, SRC-01–04, RUN-01–07, DATA-03–06, COUNT-01/03/05 and partial AT-07/09/19/21. The specification remains unchanged.

## Why this stage exists

PR #66 provided supervised **PubMed ESearch identifier** acquisition with original count/translation checks, disjoint Create Date partitioning and durable, auditable identifier pages. Those saved identifiers are **not** the records' full bibliographic metadata or abstracts.

The original `pubmed_metadata.py` parser/client and `pubmed_metadata_store.py` already implement actual EFetch requests and transactional, provenance-preserving metadata storage. This increment connects that *existing* service to the isolated local graphical interface. It does not implement a second PubMed parser, alter the approved broad OR-only queries, or assume that Medical Subject Headings (MeSH) were part of the search expression.

## Host-confirmed execution

A researcher opens a local project and selects a frozen run and PubMed source query. The **read-only EFetch preview** independently validates the selected query and the original, complete broad OR-only immutable plan, requires the original identifier checkpoint to have reached `identifiers_reconciled_metadata_pending`, and shows the exact saved query, total PubMed identifiers, metadata records already retained and those still missing. Before this stage it distinguishes `identifiers_not_acquired` from an explicitly reconciled zero-match query. No source count or missing value is invented.

The actual network path requires **another explicit Confirm**. One confirmed session requests at most **100 EFetch batches of 20 PubMed identifiers each**. The 100-request limit is an application safety budget, not a literature-search hit limit. A source with more than 2,000 records requires further manually confirmed sessions. The original National Center for Biotechnology Information (NCBI) EFetch client uses the configured contact email and optional key **only inside the trusted spawned Python worker**, a fixed HTTPS POST destination, existing pacing, XML validation, and existing request timeout. It neither silently retries a batch nor makes network requests during preview, progress refresh, journal inspection, project reopening, or export. No scheduled or unattended retrieval while the app is closed is claimed.

The original metadata ledger enforces approved-PubMed-identifier membership, idempotent re-acquisition, source-record conflict detection and **atomic** batch insertion of original source values and query memberships plus audit events. The parser rejects partial, duplicate, unexpected or unsafe XML records. If a batch fails, all previously committed metadata remain intact; the whole session reports incomplete rather than inventing missing abstracts or successful requests. On an explicitly approved later session, the existing collector skips already successfully stored identifiers. An interrupted EFetch HTTP request may have reached NCBI but not committed locally; no automatic replay is attempted. The end user must inspect the original local ledger and explicitly confirm another session. There is no durable per-HTTP-attempt reservation, provider-wide Retry-After ledger or graceful metadata-specific pause in this bounded increment; these require later reliability work, not an implicit completion claim.

## What the GUI shows and does not show

The worker runs in a separate supervised child so its HTTP and SQLite work does not block the interface. A separate existing inspection worker reads the original project during execution; the passive 2-second screen refresh reads only persisted metadata and supervisor state. The GUI reports actually saved metadata/remaining identifier counts and whether a usable abstract was **present** or **not supplied in EFetch response**, preserving the latter's important distinction from proof that no abstract exists anywhere. Full titles, author information, source abstracts, source PMIDs, API keys and personal email are not included in the GUI's progress payload or logs. Original source records remain privately retained in the project's authoritative SQLite database, and abstract redistribution rights require separate review.

A returned worker result is only a terminal operation receipt. The graphical flow also independently reads the original retained source-record index and verifies the exact run/query, original plan hash, counts, incomplete status and forbidden completion flags before releasing its active-operation lock. Failed or interrupted operations do not fabricate successful batches or a safe automatic retry.

When every original PubMed identifier has a saved EFetch record, the result is labelled `metadata_acquired_reconciliation_pending`. This is **not** a whole-source `completed_verified` state; the original source query and parent run remain incomplete. Absent abstracts, missing provider fields, cross-source deduplication, metadata conflict resolution, professional society results, comprehensive counts and reporting acceptance remain separate. `source_retrieval_verified=False` and `whole_search_verified=False` remain explicit throughout.

## Tested and unverified boundaries

Offline fixtures exercise the original approved run, saved count/identifier checkpoint, actual EFetch client/parser, transactional SQLite metadata ledger, and an isolated deterministic supervisor double. They cover no-identifier/zero-identifier distinctions, preview/cancellation with no requests, two successful batches, complete versus missing abstracts, original metadata rights provenance, attempted bad XML, partial request failure retaining earlier rows, manual restart/resumption without re-fetch of committed records, no-host-key read-only reopening, source-plan tampering, supervisor double clicks, forged terminal receipts, secret redaction and absence of GUI source calls from automated probes. The allowlisted command router tests confirmation, type strictness and cross-operation credential leaks.

No new schema, dependency, provider claim or specification change. Live EFetch source acceptance, 100-batch Windows responsiveness under real network conditions, NCBI rate/quota/reset evidence, durable request-intent journalling, cooperative metadata pause, formal complete-bibliography reconciliation, licensed export policy, global unique-publication matching and native Windows packaging remain open work.

**Mandatory merge gates:** all four Windows/Linux Python tests; applicable graphical dependency/lifecycle matrices; definitive completed exact-HEAD Codex code review **then** security review including individual receipts and finding dispositions; and explicit owner authorisation.
