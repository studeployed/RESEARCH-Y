# P1-06k3b — Source-validated pair-cache results and historical review decisions

**Baseline:** owner-merged pull request (PR) #76, `main` `768de47ee6c018392a26674e7a0bef99d613f6e8`. The authoritative `RESEARCH-Y_SPEC.md` remains unchanged. This is a bounded Phase 1 P1-06 slice of DUP-01–05, DATA-01/02/04/05/06, AUDIT-03, UI-07/09, COUNT-01/05 and AT-09/10/11/17/19/21; it is **not** release acceptance.

## Gap addressed

PR76 introduced a durable, audited, 20-row-paginated source-pair hint checkpoint from exact normalized titles, Digital Object Identifiers (DOIs), PubMed identifiers and Web of Science accessions. Its `ready_keys_only` state intentionally excluded **previously reviewed pairs without a current exact bibliographic key**. This mattered because a confirmed match or rejection is an independent recorded reviewer decision and must not disappear from the review queue when metadata is corrected or does not share a key.

This increment makes `read_candidate_queue` consume a *ready* PR76 pair checkpoint **only after** combining it with all applicable, validated original `publication_candidate_decision_v1` receipts, including historical rejections and matches whose sources no longer share an exact field. Audit receipts remain in their original immutable `audit_events` journal; **no duplicate decision register or schema migration is introduced**.

## Read-only algorithm and controls

1. Under one original project SQLite read transaction, validate the PR76 checkpoint and its PR74 source-key generation, status, source-mutation epoch and original key/pair counts. `building` or `stale` checkpoints are **never** read as complete; the PR75 source-key queue or original-source projection continues to serve results with its existing explicit resource caps.
2. Validate **every** original review receipt using the existing conservative candidate service. A receipt pair may enter the selected run's queue only if both retained source records remain supported/materialised and **at least one** source retrieval belongs to the selected run. Historical-only pairs are not imported into an unrelated run. A pair already present as an exact-key hint is not counted twice.
3. Use a **bounded B-tree keyset lookup** of at most 21 indexed exact-key pairs, merged with the next at most 21 sorted receipt-only pairs, to produce 20 chronological-by-canonical-identifier source-pair results and an exact next cursor. The total is the durable distinct exact-key pair count plus the number of applicable receipt-only pairs. More than the declared 100,000-source or 100,000-pair resource caps fails rather than silently omitting evidence.
4. Each displayed pair is compared anew by the **original** `publication_candidates._view` source and identity service. Every cached field claiming exact equality must also be **equal** in that original normalized citation comparison; contradictory or tampered hints fail closed. Original source identities, bibliographic warnings, current publication links, decision status, full decision-history count, current review event identifiers and same-run/cross-run permission status are projected from originals—not inferred from the derivative cache.
5. The page revision binds PR76 pair generation/source epoch/evidence hash, PR74 source-key generation/source epoch, canonical selected-run counts, **all** project run statuses, original queries, query/group memberships, associations and the verified decision-journal receipt history. A changed source, run, reviewer decision or link invalidates stale pagination. A forged cursor must already be a pair in the original receipt register or durable exact-key hints; otherwise it fails closed.

The same experimental Graphical User Interface (GUI) queue now recognises backend `verified_pair_checkpoint_v6` only when `pair_index_status=ready_keys_only`, with a valid generation. Existing `candidate_review_preview`, `candidate_review_decide`, `candidate_reversal_preview`, and `candidate_reversal_confirm` operations remain the sole human-approved matching authorities. The host independently rereads the same queue page before navigating to any actionable same-run pair. Cross-run pairs remain **read-only**, whether originally discovered or recorded historically.

## Disclosure and limitations

The output continues to report original counts and explicit limitations: `global_unique_publications=null`, `deduplication_complete=false`, `candidate_discovery_complete=false`, `source_retrieval_verified=false`, `verified_complete=false`. A `candidate_pair_total` is a **source-pair review queue size**, not a count of unique publications. Title/DOI matches never silently merge individual conference abstracts sharing a containing supplement. No licensed abstract body, provider credential, external network operation, new model or publication classification is added.

This increment does **not** automate building PR76 pair checkpoints from the desktop GUI. Its existing Python service must first be explicitly invoked to prepare a generation; the result browser only **reads** a ready one. A future bounded increment should expose a separate, consented start/continue/pause/reinspect workflow for those pair checkpoints, with independent post-commit audit reconciliation before production use.

The source-key cache and validated original receipt history remain authoritative. The receipt overlay is read from persisted original audit events on each page—not redundantly copied into another database table. This avoids a parallel mutating decisions store, but does not certify optimal performance for a huge project with thousands of historical decision receipts. A dedicated 100,000-record/large-decision benchmark and per-run resource-bounded acceptance tests remain outstanding; semantic correctness comes before changing review authority.
